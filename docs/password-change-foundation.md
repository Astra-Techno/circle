# S1a secure password-change API foundation

27 October 2026. Source-only backend/contract checkpoint. No new mobile password form, APK publication, deployment, reset/recovery bypass, OTP or account deletion/export is included. Live download remains Android1.0.9 build10. The owner approved sequential safety/account-controls work; the next S1b batch integrates the explained client form and local session cleanup.

OpenAPI0.3.6 adds authenticated `POST /auth/change-password`, requiring a JSON object containing only raw current_password/new_password strings. Current input is nonempty and bounded to1024 UTF-8 bytes. New input must be valid Unicode, 15–128 characters and different byte-for-byte from current. Whitespace is never trimmed. The new endpoint explicitly enforces the existing contract's15-character minimum; the legacy registration validator's lower minimum is a separate compatibility/policy alignment task for the client batch. Existing weak-password accounts can still sign in and upgrade their password.

The transaction locks the authenticated user, then rechecks the active login session under a session-row lock. It verifies the current Argon2id secret, replaces the hash, revokes ALL the user's refresh rows (therefore all associated access sessions) and deletes ALL their device registrations. It issues no replacement credentials: successful response data is exactly `{sign_in_required:true}`. Other accounts, memberships and content are untouched. Already dispatched requests/provider messages cannot be recalled; the worker's existing send-time session checks prevent future queued delivery to revoked sessions. Native cancellation/local cleanup still require S1b integration.

Wrong-current attempts return422 invalid_current_password without revocation. They commit the existing shared per-mobile failed-credential budget; the response is emitted outside the transaction so the test ResponseSent exception cannot roll it back. The existing normal per-IP rate limit also applies; the shared failure ceiling defaults to10/15minutes, returning429/Retry-After900. Validation failures never echo credentials. No request/payload logging is added.

Login previously verified a hash before storing a session without a user lock. It now reacquires the exact current user hash under FOR UPDATE and compares it byte-for-byte with the previously verified hash, rejecting a changed hash before any session insertion. The lock is held through commit. Refresh likewise takes the user lock before checking/rotating the refresh row, matching password-change lock order. This prevents a pre-change credential verification from minting a surviving session after password revocation. Scoped backend review confirmed the exact-hash-under-lock guard is sufficient without duplicate verification. This is local transaction/static review evidence, not a production concurrency/load test.
