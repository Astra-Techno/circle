## Design

The local `circle_push` Android Flutter plugin registers in both main and Firebase headless engines. Channel handlers execute on Android's main thread. One process-wide lease serializes encrypted Dart ledger transactions across engines. The app uses the default single Android process; this is not a multiprocess/distributed lock. Lock acquisition is bounded; a dead isolate holding a lease fails closed until process restart rather than expiring into concurrent writes. No HTTP runs while holding the ledger lease. Foreign scopes' pending records are retained until expiry instead of letting an old background writer prune the new account's entries.

The background processor validates the complete envelope against the configured HTTPS server and stored recipient/session before any request. It stages metadata durably, fetches current category/global/quiet-hour policy and authorized content using an in-memory token snapshot, then re-reads the real secure token store to check session scope before native display. Its client cannot refresh, persist or clear real credentials. Offline, expired access tokens and temporary failures leave reception pending for the foreground owner; permanent missing/inaccessible content is acknowledged without display. There is no background login or permission prompt.

Native display atomically checks the saved opt-in scope, app/channel permission, expiry and a bounded 512-entry scoped event history. Foreground and background both use this native path, replacing the N1c2 in-app banner. Generic lock-screen text contains no private title/body/name/media URL. Stable scope/event tags replace an existing entry on ambiguous replay; history is committed after the OS handoff. Process death between those operations may replay that tag; exactly-once delivery is not promised. Android native scope/history preferences store digests/expiry only. Account/session transport invalidation immediately queues native scope clearing and OS cancellation independently of SDK/network cleanup.

Native tap intents target the app explicitly and are immutable. Before consuming an Intent, the plugin stores its minimal envelope in an AES-GCM AndroidKeyStore encrypted queue (at most eight, expiry bounded to the envelope lifetime). Main/warm and cold launches replay it. Dart acknowledges an exact UUID only after durable open staging or verified existing reception/history; invalid scopes are discarded. Transient SDK/registration stops clear display scope but preserve unacknowledged opens. Engine detach/cancel clears only its owned event sink. The normal presenter fetches authorized content again before generating the internal route, and deleted/inaccessible taps produce a calm message. Tap metadata and credentials are never logged.

`CIRCLE_PUSH_ENABLED` remains false by default, including stable build8. The isolated Android 1.0.8+9 acceptance APK explicitly enables the client so the owner can opt in and run [device checks](push-device-acceptance.md). Stable download publication must wait for those observations. Backend flags/configuration and later event hooks are unchanged; no iOS claim is made.

## Evidence

Flutter format/analyze clean. Focused push/auth/settings suite: 50 passed; final background/native/session/presentation subset: 29 passed; deleted-content tap fallback rerun: four passed. Full suite: 564 passed, one skipped, the same 13 known Windows-baseline golden failures. No baselines regenerated. Regressions cover quiet hours, disabled preferences, missing membership/content, wrong group/comment, expired tokens without refresh, foreign server, logout/new same-account session during I/O, failed native handoff retry, cross-engine serialized staging, foreign-scope retention, exact tap acknowledgement after persistence, method-channel payload/lease behavior and malformed taps. Fake channels do not execute Android's NotificationManager or AndroidKeyStore.

Scoped static review found volatile tap handoff and clearing taps on transient stops; both were corrected and rechecked. Native build/package/certificate and publication results are recorded in the candidate release document. Backend files/contracts are unchanged; prior dedicated-circle_test 159 tests / 2,673 assertions and PHPStan evidence remain applicable. Hosted sender counters, actual FCM acceptance, background/Recents delivery, OS permission/channel behavior, cryptographic keystore behavior, notification cancellation and real cold/warm taps remain device/hosting acceptance, not established by compilation or mocks.
